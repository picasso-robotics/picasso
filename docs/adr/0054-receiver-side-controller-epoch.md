# ADR 54 — 수신자가 기체마다 제어자 세대의 바닥값을 들고 명령 다섯을 대조한다

- 상태: 확정 (2026-11-16)
- 관련: [ADR 9](0009-no-declaration-without-consumer.md) 소비자 존재 원칙, [ADR 36](0036-work-first-assignment-vs-execution.md), [ADR 51](0051-three-authority-boundaries.md) 결정 5·6·7, [ADR 52](0052-work-permit-is-a-projection.md)
- 변경 이력: 설계 문서 §15.330(검토 반영 — 결정 4·6·8 고침, 결정 11 추가)

## 맥락

ADR 51 결정 5 는 옛 발행 경로의 차단을 받는 쪽에 두고 «칸을 더할 조건» 을 계약 진입 2대 게이트로 미뤘다. 담는 쪽(mission-ops)은 실행 호스트 리스와 세대를 지었고 보내는 쪽 관문(`GatedRobotPort`)으로 잃은 프로세스의 송신을 막는다. 남은 빈자리는 둘이다. 첫째, 보내는 쪽 관문을 지나 이미 선로에 오른 명령, 그리고 만료 뒤 깨어난 옛 프로세스의 명령을 받는 쪽이 가르지 못한다(`docs/contract.md` §7.4 둘째 행). 둘째, 새 소유자가 «옛 경로가 막혔다» 는 증거를 얻을 길이 없어 만료 인수는 운영자 확인을 기다린다(ADR 51 결정 7).

수신자 둘(미믹·`adapter-host`)은 지금 헤더의 `client_id` 를 읽지 않고, 조작은 태스크 id 만 맞으면 누구의 요청이든 받는다. `adapter-host` 의 명령은 호스트 잠금 밖에서 링크 잠금만 쥐고 벤더로 가므로(§15.269) 입구에서 한 번 대조하는 것만으로는 «입구를 지났으나 아직 안 보낸 옛 명령» 이 남는다.

## 결정

**결정 1. 칸은 헤더 하나이고 방향마다 뜻이 다르다.** `MessageHeader.controller_epoch = 14`(uint64). 요청이면 발신자의 세대, 응답이면 **수신자가 지금 든 그 기체의 바닥값**이다. 요청값을 되울리지 않는다. 0 은 요청에서 «싣지 않음», 응답에서 «대조 안 함» 이며 대조하지 않는 수신자와 이 칸을 모르는 옛 수신자가 같은 뜻으로 0 을 낸다. MQTT 발행에는 싣지 않는다. 계약 0.12.0 이고 추가라 major 는 그대로다. 헤더 표(`HeaderColumns`)는 요청·응답 열에 이 칸을 두고, 0 이 값인 칸(`ZERO_IS_VALUE`)으로 따로 적는다 — 비어 보여도 누락이 아니다.

**결정 2. 바닥값의 키는 `robot_id` 다.** ADR 51 결정 2 의 로봇 제어 권위 키와 같다. 멱등 키 `(task_id, revision)`·태스크 장부에는 세대를 두지 않는다 — 새 소유자의 같은 키 재전송은 기존 핸들에 붙어야 한다. 판단 기록과 내보내기에도 **세대 칸은 없고** 판은 그대로다(판단 기록 6·내보내기 10). 다만 기존 자유 문자열 칸에 새 값 둘이 실릴 수 있다 — 실행 자취 `CONTROLLER_REFUSED`(세대·바닥값이 든 문장)가 인시던트 근거 창 `evidenceWindow[].kind/detail` 로, 단위 메모 `FENCE_REFUSED` 가 판단 기록 `verdict.note` 로. 분기할 칸이 아니다(자취 종류 `DOUBT_ATTACHED`·`CANCEL_UNSENT` 가 판을 안 올리고 더해진 선례와 같다).

**결정 3. 수신자 모드는 둘이고 기본은 대조하지 않는다.** `UNFENCED`(기본)는 오늘 거동이다 — 비교·상승·저장이 없고 응답 바닥값은 0 이다. `FENCED` 는 명령 다섯(`StartTask`·`RetryTask`·`PauseTask`·`ResumeTask`·`CancelTask`)에 대해 `e = 0` 을 거부하고, `0 < e < F` 를 거부하고, `e = F` 를 통과시키고, `e > F` 면 바닥값을 **저장한 뒤** 올리고 처리한다. 저장이 던지면 그 요청은 실패다. 대조는 라우팅·계약 개정판 대조·식별 정보 대조를 지난 뒤에 한다. 무엇이 바닥값을 올릴 수 있는지는 주입하는 `EpochAdmission` 이 정하고, 저장소가 주는 구현은 «검증을 지난 명령 다섯과 `GetSnapshot`» 하나다. 판정은 `contracts` 의 `ControllerFence` 한 벌이다 — 수신자 둘이 같은 판정을 써야 하기 때문이다(`RequestHeaders` 가 거기 있는 까닭과 같다).

**결정 4. 거부는 계약의 거절이다.** `REJECTION_CODE_STALE_CONTROLLER = 15` 와 `Rejection.requested_controller_epoch`·`controller_epoch_floor`. 까닭은 두 칸으로 갈린다(`StaleReason`) — 요청 세대 0 이면 필수 누락(`EPOCH_MISSING`), 2^63 이상이면 범위 밖(`OUT_OF_RANGE` — 칸은 uint64 지만 받는 범위는 1..2^63-1 이다), 바닥값보다 낮으면 밀려남(`BELOW_FLOOR`), 바닥값 이상이면 올릴 자격 없음(`NOT_ADMITTED`). 밀려남은 셋째 하나다. gRPC 상태로 내지 않는다 — 상태는 보내는 쪽에서 «나갔는지 모름» 으로 읽혀 조회 재전송이 돈다. 거부한 명령은 벤더도 장부도 건드리지 않는다.

**결정 5. 읽기는 거부하지 않는다.** `WatchTask`·`GetCapabilities`·`ReplayEvents`·`Negotiate`·`GetKnownSiteNames` 는 올리지도 거부하지도 않는다. 낮은 세대의 단건 읽기와 새 구독은 통과하고 응답에 바닥값이 실린다. 열린 스트림은 권위를 갱신하지 않고 끊지 않는다. 수락된 태스크는 그대로 진행해 끝난다(ADR 51 결정 4 의 «진행 중 명령은 보존되고 관리자 세대만 바뀐다»). ADR 51 결정 7 의 «관측은 계속» 이다.

**결정 6. 인수 확인은 실제 `GetSnapshot` 이다.** 요청 세대가 그 기체의 바닥값 이상이고 수신자가 대조하면, 바닥값을 저장한 뒤 올려 낮은 세대의 새 진입을 막고, 그보다 낮은 세대로 이미 입구를 지난 명령(조작 대기 포함)이 장부 반영까지 끝나기를 기다린 뒤 스냅샷을 짓는다. 답은 `GetSnapshotResponse.fence_status`(`FenceStatus`) — 받은 저장의 실제 내구성대로 답한다 — 메모리 저장이면 정리 여부와 무관하게 `VOLATILE`, 기한을 넘겼거나 결과를 모르는 변경 호출이 남았으면 `DURABLE_PENDING`, 아니면 `DURABLE_CONFIRMED` 다. 결과를 모르는 변경 호출은 셋이다 — 접수, 개정 갱신(`adapter.update`), 조작(일시정지·재개·취소·재시도)의 `LINK_IN_DOUBT`. **미확정을 걷는 근거는 해소의 증명뿐이다.** 접수와 갱신은 걷지 않는다 — 장부에 없는(또는 옛 리비전인) 태스크의 결과를 벤더에 물을 길이 어댑터 포트에 없고, 어댑터의 «쉼»(지역 상태)이나 다른 접수의 수락은 증명이 아니다. 같은 키 재전송에는 다시 보내지 않고 같은 미확정 답을 준다. 조작은 펌프가 그 태스크의 종착을 읽고 어댑터가 그 읽기를 벤더 관측이라 말할 때(`RobotAdapter.pollObservesVendor`, 기본 거짓 — 링크 잠금 안에서 상태와 함께 읽는다)만, 그리고 그 읽기를 계획할 때 본 바로 그 조작(등록 때 매긴 토큰이 같은 것)만 걷는다 — 같은 태스크의 새 조작은 새 토큰이라 앞 읽기가 지우지 못한다. 결과를 모르는 조작이 남은 태스크는 종착으로 적혀도, 어댑터가 한 번이라도 벤더 관측이라 말했으면(한 번 참이면 계속 참 — 그 값은 어댑터 수명 동안 바뀌지 않아야 한다) 펌프가 계속 읽어(상태는 다시 적지 않는다) 다음 벤더 관측 종착 읽기가 그 토큰을 걷는다. 벤더 관측을 안 주는 어댑터면 걷을 근거가 안 나오므로 다시 읽지 않는다. `adapter-host` 재시작은 메모리의 미확정을 지우며 그것은 해소의 증명이 아니다(한계 대장 «§15.330 · 미확정 접수»). 뒤 조작의 거절·미지원·링크 오류 답은 앞 조작의 결과를 알려 주지 않아 걷지 않는다. 증명이 없으면 `DURABLE_PENDING` 이 남고 운영자 확인으로 간다 — 자동 재개를 막을 뿐이라 안전 쪽이다. 기다린 뒤 바닥값을 다시 보고, 그 사이 더 높은 세대가 올렸으면 인수 확인이 아니다(`UNSPECIFIED`). 대조하는 수신자도 아직 한 번도 오르지 않은 기체에는 머리말 바닥값 0 을 싣는다 — «대조 안 함» 과 머리말만으로는 갈리지 않고 `fence_status` 가 가른다. 인수 확인이 아닌 읽기는 `UNSPECIFIED` 다. `DURABLE_CONFIRMED` 의 뜻은 «이 응답 뒤로 낮은 세대의 명령이 벤더 송신을 새로 시작하지 못하고, 앞서 시작한 송신은 장부에 반영돼 이 스냅샷에 있다» 이다. `adapter-host` 는 기다리는 동안 호스트 잠금을 쥐지 않는다(`GetSnapshot` 이 잠금 밖 메서드가 됐다). 링크 잠금 안, 벤더 호출 바로 앞에서 한 번 더 대조한다(방어). 저장소는 주입 인터페이스(`FenceStore`)이고 `adapter-host` 는 파일 구현(`FileFenceStore` — 기체마다 숫자 하나, 임시 파일과 이름 바꾸기, 적용 전 기록, 손상이면 서지 않음, 디렉터리 배타 잠금)을, 미믹은 메모리 구현(시험·일회성 전용)을 쓴다. 파일 구현은 이름 바꾸기 뒤 디렉터리를 내리되, 디렉터리를 못 여는 파일 시스템(윈도)에서는 못 한다 — 전원이 나가면 앞 값으로 돌아갈 수 있다. 저장이 던지면 두 수신자 모두 `FAILED_PRECONDITION` 이다.

**결정 7. 보내는 쪽은 세대를 생성 때 정하고 바뀌면 보내지 않는다.** `PicassoClient` 는 세대 공급자를 받아 처음 본 0 아닌 값을 붙잡는다. 공급자가 다른 값을 내면 명령을 선로에 내지 않는다(`ControllerEpochChanged` → 포트의 `CommandNotSent`). 프로세스 하나는 세대 하나다 — 바뀌면 클라이언트와 포트를 새로 만든다. `RequestHeaders.build` 는 세대 인자(기본 0)를 받는다. `RobotPort` 시그니처는 그대로다.

**결정 8. 실제로 밀려났을 때만 보내는 쪽이 닫고 알리고, 미들웨어는 어떤 세대 거절도 일반 실패로 읽지 않는다.** `ClientRobotPort` 는 자기 세대가 0 이 아니고 수신자가 알려 준 바닥값이 그보다 높을 때만(`BELOW_FLOOR` 거절, 또는 읽기·스트림·능력 응답 머리말의 더 높은 바닥값) 그 포트의 명령을 닫는다(래치) — 그 뒤의 출발·취소는 선로에 안 나가고 `CommandNotSent` 다. 처음 닫을 때 담는 쪽에 `onSuperseded(robotId, mine, floor)` 를 한 번 낸다. 밀려남이 아닌 거절(세대 0·범위 밖·자격 없음)은 그 명령만 거절된 것이라 닫지도 알리지도 않는다 — 세대 0 포트 하나가 대조하는 수신자 하나 때문에 다른 기체의 명령까지 막히지 않는다. 미들웨어는 그것을 설정 오류로 보고 정상 경로를 막지 않는다 — 같은 단위의 출발·개정 갱신 다시 내기를 조회와 같은 간격(`LOOKUP_INTERVAL`)으로 늦추고, 미확정 조회의 그 거절은 하위가 답한 조회로 횟수를 써 유예 뒤 운영자 보류로 간다(보류 사유는 «수신자가 세대 거절로 답함» 으로 적는다). 권위를 잃었다고 판단하는 것은 담는 쪽이다. 능력 조회처럼 머리말을 돌려주지 않는 읽기는 클라이언트가 본 가장 큰 바닥값(`PicassoClient.floorSeen`)으로 본다. 미들웨어는 거절 응답을 출발 셋(첫 출발·개정 갱신·미확정 조회)의 공통 정산 자리(`settleIssue`)와 취소의 두 수신 자리(`cancelRobot`·`pollRobotCancel`)에서 일반 실패 처리 전에 받는다. 출발은 «보내지 않음»(`Issue.NotSent`, 거절은 `refusal` 칸에 실린다), 취소는 «닿지 않음» 으로 접는다 — 수신자가 벤더도 장부도 건드리지 않았으므로 뜻이 참이다. 그러나 자취는 둘을 가른다. 실행 자취에 `CONTROLLER_REFUSED` 로 그 거절(수신자가 답했는지·까닭·요청 세대·바닥값·받은 시각)을 같은 실행·기체·까닭·바닥값마다 한 번 남기고, 단위 메모도 «보내지 않음» 이 아니라 세대 거절로 적는다. 밀려남만 발행 관문에 기체마다 남는다 — 관문이 그 기체의 새 발행을 `AUTHORITY_NOT_HELD` 로 막고(포트가 머리말로만 안 밀려남도 `RobotPort.controllerRefusal` 로 같다), 그 기체의 미확정 유예·인시던트 판단(미확정의 스냅숏 부착·높은 리비전 보류·조회·물리 관측·운영자 보류, 끊긴 기체에 건 취소의 보류, 붙기 전 취소의 보류)이 멈춘다. 밀려남은 걷지 않는다 — 세대는 되돌아가지 않고 다시 서려면 새 프로세스다. 자취의 «한 번» 열쇠는 실행마다 따로라 실행과 함께 사라진다. 그래서 단위 실패·재작업·인시던트·회복 제안으로 가지 않는다 — 앞서 답을 잃은 조회가 있는 미확정 단위와 미확정 중의 키 취소도 같다. 송신 뒤 응답 유실은 계속 `InDoubt` 다.

**결정 9. 발행 관문의 첫째 입력은 `AuthorityPort` 다.** 널이면 오늘 거동(막지 않음)이다. 붙이면 기체마다 «쥠/아님+까닭» 을 묻고, 아님·답 없음·포트 예외는 `IssueVerdict.Withheld` 와 `PermitCause.AUTHORITY_NOT_HELD` 로 막는다. 새 발행 셋만 막고 취소는 막지 않는다 — 취소는 보내는 쪽 권위와 받는 쪽 대조가 막는다.

**결정 10. ADR 51 결정 7 의 인정 증거에 셋째를 더한다.** «그 기체에 닿는 모든 명령 경로가 모인 수신자의 `DURABLE_CONFIRMED` 인수 확인» 이다. 조건은 수신자가 하나(같은 기체를 맡는 `adapter-host` 가 둘이 아님)이고 직접 벤더 접근이 없는 것이다. 이 조건은 코드가 집행하지 못하므로 배포 전제다. 자동 재개(기체마다 확인한 기체부터 발행 열기)는 담는 쪽의 다음 단계가 짓는다.

**결정 11. 식별 정보 대조가 세대 대조보다 먼저다.** 두 수신자 모두 조작 넷의 핸들 `robot_id` 가 헤더와 다르면 세대를 보기 전에 `IDENTITY_MISMATCH` 로 거절한다 — 어긋난 요청이 헤더 기체의 바닥값을 영속 상승시키지 못한다.

## 상위 표준·벤더 어휘 대조 (ADR 36)

## 왜 이 모양인가

- 수신자가 «지금 유효한 권위» 를 알 수는 없다 — 리스는 담는 쪽 DB 에 있다. 대신 새 소유자가 발행 전에 읽기로 바닥값을 먼저 올리고(인수 확인), 응답으로 확인한 기체부터 발행한다. 이것이 막는 것은 «두 발신자의 동시 명령» 이고 «같은 세대의 만료 권위 행사» 는 못 막는다.
- 확인 응답이 «숫자를 저장했다» 이면 입구를 지난 옛 명령이 응답 뒤에 벤더로 나간다. 그래서 확인은 그 명령들이 장부에 반영되기를 기다리고, 벤더 호출 직전에 다시 댄다.
- 되울린 바닥값은 «대조한다» 의 증명일 뿐 «재시작 뒤 보존한다» 의 증명이 아니다 — 메모리 수신자도 같은 값을 되울린다. 그래서 보존 여부를 `fence_status` 로 따로 말한다.
- 읽기를 거부하면 세대를 모르는 관측 도구와 옛 호스트의 관측이 끊긴다. 밀려남은 응답 머리말의 바닥값으로 안다.
- 거부를 `Issue` 의 새 변형으로 두지 않았다 — 분기 자리가 여러 파일로 퍼진다. 래치 때문에 포트당 거부 응답은 사실상 한 번만 온다.

## 고르지 않은 것

- 세대를 멱등 키·태스크 장부·판단 기록에 넣기, 옛 스트림 강제 종료, 낮은 세대 읽기 거부, gRPC 상태로 거부, 헤더에 리스 만료 시각(시계 동기 전제), 전용 대조 RPC, 바닥값 자동 초기화.
- `client_id` 허용 목록 — 인증이 없어 실수만 막고, 올리는 요청을 명령 다섯과 `GetSnapshot` 으로 좁힌 것이 그 실수 대부분을 막는다.
- 세대 0 을 양수 관측 뒤에도 명령에 허용하기 — 0 이 우회로가 된다. 대조하는 수신자는 0 명령을 처음부터 거부한다.

## 대가

- 같은 세대의 만료 권위, 인증 없는 세대 오염(수동 복구만), DB 후퇴·같은 번호 재발급, 수신자 둘이 한 기체, 기본이 대조하지 않음, `adapter-host` 의 저장 경로를 주지 않은 대조의 휘발, 나갔는지 모르는 접수의 답, 저장 실패의 보내는 쪽 미확정 — 한계 대장 «§15.330» 행들.
- 대조하는 수신자에는 세대를 싣지 않는 도구(`client` CLI 의 직접 `StartTask` 등)의 명령이 거부된다. 그런 도구는 권위를 쥔 호스트를 거쳐야 한다.
- 플릿·셀 HTTP 경로는 picasso 계약이 아니라 이 결정 밖이다(한계 대장 «§15.219 · 플릿 경로»).

## 다른 결정과의 관계

- ADR 51 결정 5 의 «칸을 더하지 않는다» 를 이 결정이 넘겨받아 칸을 지었다. 결정 6 의 첫째 입력을 `AuthorityPort` 로 열었다. 결정 7 에 셋째 증거를 더했다(결정 10).
- ADR 52 의 발행 관문 모양(기체마다 판정, 던지면 막음, 취소는 안 막음)을 첫째 입력도 그대로 쓴다.
- ADR 9: 칸마다 소비자가 있다 — 요청 세대는 수신자 둘의 대조, 응답 바닥값은 `ClientRobotPort` 의 밀려남 판정과 담는 쪽의 인수 판정, 거부 코드는 미들웨어의 소비, `fence_status` 는 담는 쪽의 기체별 재개 판정이다.

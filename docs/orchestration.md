# 오케스트레이션 — 세 계층과 자원 소유

이 문서는 **무엇을 누가 승인하는가**를 적습니다. 자원마다 소유자가 하나 있고, 그 자원으로 향하는 명령은 소유자의 게이트를 통과합니다. 레지스터의 빈 칸은 곧 무승인 경로이며, 그 자리가 사고가 발생하는 지점입니다.

관련 결정: [ADR 43](adr/0043-entitlement-declared-outside-judged-inside.md) 자격의 외부 선언과 내부 판정 · [ADR 38](adr/0038-mission-layer-schema-is-ours.md) 미션 계층 내재화 · [ADR 34](adr/0034-semantic-binding-unowned.md) 결속의 어댑터 외 격리 · [ADR 35](adr/0035-site-names-live-in-the-robot.md) 사이트 명칭의 기체 내부 저장 · [ADR 9](adr/0009-no-declaration-without-consumer.md) 소비자 존재 원칙.

## 1. 오케스트레이션은 한 덩어리가 아니라 세 계층이다

| 계층 | 무엇을 정하는가 | 실패 시 결과 | 소유자 |
|---|---|---|---|
| **L1 작업 배정** | 무엇을, 언제, 누구에게 — 재할당 및 우선순위 | 느리거나 나쁜 응답 (처리량 손실, 특정 셀 기아) | 정책 계산 주체. 안이든 밖이든 **결정권은 없음** |
| **L2 실행 보증** | 그것이 실제로 수행되었는가, 아니라면 무엇을 아는가 | **거짓을 참으로 단정** | **본 저장소** (ADR 38) |
| **L3 경로·교통** | 물리적으로 어떻게 이동하는가, 누가 바닥을 사용하는가 | 충돌 및 교착 | 자원 소유자 — 플릿 또는 조정층 |

두 방향의 의존이 있습니다.

- **L1 은 L2 없이 성립하지 않습니다.** 상태 기반 배정의 전제는 상태가 참이라는 것입니다. 상태를 신뢰할 수 없으면 L1 은 쓰레기를 최적화합니다.
- **L3 을 L2 가 대신할 수 없습니다.** 바닥을 소유하지 않으므로, 사본을 가져와도 그 값을 참으로 유지할 권한은 따라오지 않습니다.

ADR 38 은 L2 를 내재화한 결정이며, 밖에 남긴 것은 L3 입니다. **L1 이 배제된 적은 없습니다** — 셀 내부의 L1 은 범위 안이고 아직 구현되지 않았습니다(§15.153).

## 2. 자원 소유 레지스터

**한 자원에 소유자는 하나입니다.** 소유가 겹치면 우선순위 규칙을 추가하지 않고 소유 경계를 다시 긋습니다. 그리고 **소유자가 없는 자원에는 명령을 내지 않습니다** — 자격은 선언으로만 발생합니다.

| 자원 | 소유자 | 게이트 (승인 지점) | 현재 |
|---|---|---|---|
| 셀 내 기체의 작업 배정 | 본 저장소 | `Middleware.admits` — 순수 술어. 고르지 않고 상태를 바꾸지 않는다. 재할당은 `reassign` 이 진동 방지를 걸어 판정 | 있음 (ADR 41) |
| 셀 내 슬롯·지그·버퍼 점유 | 본 저장소 | `Middleware.submit` → `occupancyViolation` — 자리 경쟁과 `REQUIRED` 단위의 목적지 점유·목적지 미관측(`destinationViolation`), 출발 결품, 출발 미관측. 출발 결품은 그 자재를 든 다른 자리를 계산해 레지스터에 남기며 목적지 점유·미관측과 출발 미관측은 대체 자리를 계산하지 않고 레지스터에 남기지 않음 | 있음 (§15.183 — 자리 경쟁은 레지스터에 안 남는다) |
| 셀 내 작업 공간(구역 겹침) | 본 저장소 | `Middleware.admits` → `workspaceViolation` — 같은 구역의 두 기체를 동시에 안 보냄 | 있음 (§15.163 — 구역 단위라 성김) |
| AMR 개체 및 이송 | 플릿 | `AmrFleetPort.dispatch` — `null` 이 거부 | 있음 |
| 통로·층 점유 (AMR) | 플릿 | 플릿 내부 | 있음 (플릿 소관) |
| 통로·층 점유 (걷는 기체) | **미정** | `Middleware.admits` → `unownedFloor` — 소유자 없는 자리로는 보내지 않음 | **구멍** (§15.154). 절차는 §5 |
| 조치의 자동 승인 권한 | 현장 — 선언하는 사람 (ADR 43·44) | `Middleware.attemptApproval` → `scopeRefusal` — 선언 없는 승인 시도를 거절하고, 값도 선언과 관측에서만 채운다. 사람의 문(`Middleware.approveRemedy`)은 값을 들고 오므로 선언을 안 본다 | 있음 (§15.3 — 식별 정보는 위조 가능하며 부인방지가 아니라 조사 단서다) |
| 상위 작업 순서 | MES | MES 측 | 있음 (계약 밖) |
| 셀 설비의 상태 관측 | 셀 설비 | `CellSignals.observe` — `null` 은 빈 자리가 아니라 **말이 없음** | 있음 |
| 셀 설비의 이름 있는 신호 | 셀 설비 | `CellSignals.signal` — `null` 은 기대 값이 아님이 아니라 **못 읽음** 이다. 설비 대기는 기다리고 기한이 판정하며, 주소 매핑은 드라이버의 일 | 있음 |
| 임무 정의의 활성 버전 | 본 저장소 | `InMemoryMissionCatalog.activate` → `MissionValidator.validate` — 활성화는 검증(노드 id · 기한 · 신호 · 자원 · 스킬 · 안전 · 출발 관측 · 목적지 관측)을 지나야 서고 거부면 활성 버전이 그대로다. 새 작업 지시부터 적용되며 진행 중인 실행은 쥔 버전으로 끝난다. 소유는 활성화 판정의 소유이고 정의를 쓰는 사람은 시운전 · 통합 엔지니어다 | 있음 |
| 자리 이름 ↔ 좌표 결속 | 기체 세계 모델 또는 상위 사이트 정본 (ADR 34 §4) | 기체 질의 (ADR 35) 앞에 `SiteBindingCheck` — 지도 버전과 개체 캘리브레이션 버전 두 차원을 대조 | 있음 (§15.156 — 정본 구현체는 배치가 붙인다) |
| 셀 안전 상태의 새 발행 허가(정보 투영) | 현장 안전 계통 — 원천 (ADR 32·52) | `Middleware.pump` → `IssuingGate.check` — `WorkPermitPort.read` 의 값. PERMITTED 가 아니면(모름 포함) 새 로봇 명령을 안 냄. 취소·관측은 안 막음 | 있음 (붙이지 않으면 안 막음) |

**게이트 칸이 대는 기호는 코드와 대조됩니다** — `DocumentClaimsTest` 의 «자원 소유 대장이 대는 관문이 코드에 실재한다». 이름이 바뀌거나 사라지면 이 표가 아니라 그 시험이 먼저 빨개집니다.

### 이 레지스터를 읽는 법

- **「없음」과 「구멍」은 다릅니다.** 「없음」은 소유자가 정해져 있고 게이트만 아직 안 만든 것이고, 「구멍」은 **소유자 자체가 없는 것**입니다. 앞은 만들면 닫히고 뒤는 먼저 소유를 정해야 합니다.
- **구멍이 있는 동안의 올바른 상태는 그 자원을 쓰지 않는 것입니다.** 무승인 통행을 허용하는 선택지는 없습니다.
- 레지스터에 없는 자원이 나타나면 그것을 먼저 이 표에 올립니다. 표에 없는 자원으로 나가는 명령은 아무 게이트도 통과하지 않은 명령입니다.

## 3. 배선도

점선은 **아직 없는 것**입니다. 자리와 방향만 확정해 둡니다.

```mermaid
flowchart TB
  MES["상류 MES·WMS<br/>작업 순서 소유"]
  DISP["L1 배정 정책<br/>셀 내 또는 전역<br/>결정권 없음 · 제안만"]
  OP["운영자<br/>통지 수신 · 승인 · 진단"]

  subgraph PIC["본 저장소 — L2 실행 보증"]

    TICK["pump — 단일 적용자<br/>상태를 바꾸는 주체는 하나"]

    GATE --> TICK --> OUT
  end

  DISP -.->|순위 목록 제안| GATE
  DISP -.->|직접 요청| FLEET
```

**읽는 법 셋.**

- **게이트를 지나지 않는 화살표가 있어서는 안 됩니다.** `DISP → ROB` 같은 선이 그려질 수 있다면 그것이 미들웨어 우회입니다.
- **본 저장소는 인시던트 소비자를 호출하지 않습니다.** 적재하고 끝냅니다 — 소비자에게 의존하면 소비자가 정지할 때 인시던트 처리가 함께 멈춥니다.
- **좌표와 프레임은 어댑터에서만 나타납니다.** 공통 계층은 이름만 압니다. 계약의 `location` 은 문자열이며 좌표가 아닙니다(설계 §4.3).

## 4. 지금 없는 것

정직하게 세 하위 범주로 나눕니다.

| 하위 범주 | 항목 |
|---|---|
| **선언만 있고 구현은 없음** | 정량 사전 조건(적재 질량·무게중심 — 관측하는 어댑터가 없음, §15.143) |
| **범위 안이고 미구현** | 없음 — 레지스터의 아홉 자원에 모두 게이트가 있다 |
| **범위 밖 — 소유자가 다름** | 전역 배차·라우팅, 통로 교통 조정, 기능안전 기능(안전 경계는 [ADR 32](adr/0032-safety-boundary.md), 그 상태의 정보 투영은 [ADR 52](adr/0052-work-permit-is-a-projection.md) 로 범위 안) |
| **구멍 — 소유자 미정** | 걷는 기체의 통로·바닥(§15.154) |

소유자가 없는 동안의 올바른 상태는 **그 자원을 쓰지 않는 것**입니다. `Middleware.admits` 가 소유자 없는 자리로 향하는 작업 지시를 작업 수락 시점에 거절합니다. 무승인 통행을 허용하는 선택지는 없습니다.

## 5. 통로 소유자를 정하는 절차

**소유자 신설은 시스템 신설이 아닙니다.** 소유자를 정하는 일의 정체는 «누가 그 자원의 값을 참으로 유지할 수 있는가» 를 정하는 것이며, 구간을 잘라 기존 소유자에게 주면 시스템이 하나도 늘지 않고 소유자가 생깁니다. 그래서 권고 순서가 아래와 같습니다.

| | 방법 | 얻는 것 | 대가 |
|---|---|---|---|
| **D** | 물리로 분리 — 통로를 겹치지 않게 배치 | 문제가 발생하지 않음. 소프트웨어 0 | 공간 및 레이아웃 제약 |
| **C** | 구역을 잘라 기존 소유자에게 배정 | 새 시스템 없음. 기존 게이트 재사용 | 구간 경계가 또 하나의 공정 간 인계 지점 |
| **B** | 상위 조정층 도입 | 다벤더 전제의 표준적 해법. 기종 간 계산 가능 | 시스템 하나 증가. 새 단일 장애점 |
| **A** | 플릿 벤더가 걷는 기체까지 수용 | 교통 로직과 지도가 이미 존재 | 벤더 종속. 타사 기체 수용 유인이 벤더에 없음 |

**승격 트리거를 미리 적어 둡니다.** 겹치는 구간이 셋을 넘거나 바닥을 공유하는 벤더가 셋 이상이 되면 C 에서 B 로 올립니다. 조건을 먼저 적어 두면 나중에 즉흥적으로 결정되지 않습니다.

**본 저장소가 구간 소유자가 되는 경우**(C)에는 그 구간의 예약 게이트를 내놓습니다. 무한 책임 프록시와 다른 점은 하나입니다 — **소유한 것만 승인합니다.** 소유하지 않은 옆 구간의 요청을 대신 받으면 그때 프록시가 됩니다.

### 구간 예약 포트의 모양

**아직 짓지 않습니다.** 구현체도 소비자도 없으므로 계약에 넣지 않고(ADR 9), 코드로도 두지 않습니다. 자리와 방향만 확정합니다.

| 항목 | 규약 |
|---|---|
| 요청 | 구간과 기간을 지정. 소유자가 판정 |
| 거부 | **정상 경로**. 거절되면 그 구간을 쓰지 않음 |
| 유효 기간 | 빌린 권한은 만료됨. 만료되면 다시 요청하거나 손을 놓음 |
| 무응답 | **성공도 실패도 아님**(`IN_DOUBT`). 스냅숏 부착 우선, 미부착 시 간격(`LOOKUP_INTERVAL`) 기반 유예(`inDoubtGrace`) 시간 예산 재조회, 미해결 시 운영자 보류 |
| 거부 이유 | 이미 있는 어휘로만. 새 이유 코드를 늘리면 내부 판정 규칙이 계약으로 유출 |

**요청하는 쪽의 계약은 따로 적었습니다.** 위 표는 본 저장소가 **구간 소유자일 때** 내놓을 게이트입니다. 본 저장소가 걷는 기체를 대신해 **다른 소유자에게 요청하는** 쪽의 메시지·순서·실패 처리와, 배정 정책(L1)과 주고받는 것은 [피어 시스템과의 통신](superpowers/specs/2026-09-25-peer-systems-dispatch-and-space-design.md)이 정합니다. 소유자가 누구로 정해지든 그 계약은 같습니다.

## 6. 인시던트 조회면의 모양

**아직 짓지 않습니다.** 소비자가 붙는 시점에 그 PR 안으로 들어옵니다(ADR 9). 여기서는 자리와 규약만 확정하며, 규약을 먼저 적어 두는 이유는 읽는 쪽이 추측으로 수신기를 만들지 않게 하기 위함입니다.

**프로세스 밖 경로는 본 계층의 것이 아닙니다.** `picasso` 는 라이브러리이며 진입점도 HTTP API 표면도 영속화도 없습니다. 이는 결핍이 아니라 경계입니다 — 본 계층이 프로세스를 소유하면 그 프로세스의 가용성이 곧 실행 보증의 가용성이 됩니다. 조회면을 밖으로 내는 일은 본 계층을 담는 쪽의 몫이며, 저장소 안에서 프로세스와 영속화와 감사 기록을 이미 보유한 것은 `registry` 하나입니다. 어느 쪽이 담을지는 ADR 43 의 자격 선언과 같은 성질의 배치 결정입니다.

**본 계층이 보증하는 것은 순서와 식별자입니다.** 적재는 덧붙이기만 하고 지우지 않으며, 식별자는 불투명한 값입니다.

| 항목 | 규약 |
|---|---|
| 전송 | 본 계층이 정하지 않음. 담는 쪽이 HTTP·파일·DB 중 무엇으로 내든 본 계층의 코드는 동일 |
| 열거 | 열린 순서대로. 덧붙이기만 하고 지우지 않음 |
| 커서 | **마지막으로 읽은 식별자.** `incident-N` · `search-N` 의 형식을 분해해 번호를 추출하지 않음 — 그 형식을 대조하는 시험이 없으므로 묶이는 즉시 깨짐 |
| 증분 조회 | 현재는 전량 조회뿐(`incidents()` · `remedySearches()`). `after` 인자는 소비자와 함께 들어옴 |
| 처리 표시 | 읽는 쪽의 상태. 본 계층은 누가 어디까지 읽었는지 모르며, 알면 소비자마다 상태가 생김 |
| 영속화·상한 | 담는 쪽의 몫. 본 계층의 적재는 프로세스 수명과 같고, 보존 상한(`Retention`)을 넘으면 오래된 것부터 내림(§15.166). |

**거부와 인시던트는 다른 적재입니다.** 거부는 실행을 만들지 않으므로 인시던트 번들이 되지 못하며(§15.164 의 변경 이력), 탐색 결과는 (기체, 작업 지시)를 조회 키로 하는 별도 레지스터에 남습니다. 읽는 쪽은 둘을 각각 열거합니다.

### v1 에서 담는 쪽 — 파일 내보내기

§5 의 통로 소유자와 같은 모양입니다. 지금은 가장 싼 것을 쓰고 승격 조건을 미리 적습니다.

| | 방법 | 얻는 것 | 대가 |
|---|---|---|---|
| **C** | 시나리오 실행기가 두 레지스터를 파일로 내보내고, 읽는 쪽이 그 디렉터리를 주기 스캔 | 프로세스도 모듈도 늘지 않습니다. 인코딩이 순수 함수이므로 **인프라 없이 시험이 물립니다** | 실시간이 아닙니다. §15.166 의 소유자가 생기지 않습니다 |
| **B** | 얇은 호스트 모듈 하나가 미들웨어를 세우고 두 레지스터만 조회로 노출 | 경계가 깨끗합니다. 양쪽 모듈의 성격이 변하지 않습니다 | **호스트할 대상이 아직 없습니다.** 포트 여섯 중 실제 하드웨어 구현체를 가진 것은 `ClientRobotPort` 하나이며 나머지는 `None` 입니다 |
| **A** | `registry` 가 담습니다. 미들웨어를 그 프로세스 안에 세우고 조회 엔드포인트로 노출 | 프로세스·영속화·감사 기록이 이미 존재합니다. §15.166 의 소유자가 생깁니다 | **레지스트리 정지가 인시던트 조회 정지가 됩니다.** 설정 평면이 실행 평면의 적재를 들게 됩니다 |

**결정 근거는 하나입니다 — 아직 호스트할 것이 없습니다.** `src/main` 어디에서도 미들웨어를 생성하지 않으며, 생성하는 곳은 시험 스물둘뿐입니다. 실행 계층을 실제로 구동하는 유일한 주체가 시나리오 구동기이므로, v1 에서 레지스터를 밖으로 내보내는 주체도 그것입니다. **존재하지 않는 배치를 위해 호스트를 먼저 짓지 않습니다**(ADR 9 와 같은 규율).

**승격 조건을 미리 적습니다.** 아래 중 하나가 성립하면 A 로 올립니다.

- 조회가 **실시간**이어야 합니다 — 스캔 주기가 요건을 충족하지 못하는 경우
- 적재가 **프로세스 수명을 넘어** 남아야 합니다 — §15.166 의 소유자가 필요해지는 시점
- 읽는 쪽이 **둘 이상**이 됩니다 — 한 디렉터리를 여럿이 스캔하면 처리 표시가 소비자마다 흩어지고, 그 상태의 소유자가 필요해집니다

**B 는 중간 계단이 아닙니다.** 실제 배치가 생기면 그 호스트는 포트 여섯을 모두 들어야 하며, 그것은 본 결정의 대상이 아니라 배치 프로젝트입니다. 두 레지스터만 내는 프로세스를 따로 세우면 그 프로세스는 존재 이유가 하나뿐이고, 진짜 호스트가 생기는 날 폐기됩니다.

### v1 의 적재 규약

읽는 쪽의 골격이 서서 ADR 9 의 조건이 충족되었으므로 인코딩이 들어왔습니다. **인코딩과 전송을 가릅니다** — `LedgerExport` 는 문자열만 만들며 파일도 소켓도 자기 시계도 건드리지 않습니다. 순수 함수이므로 인프라 없이 시험이 물리며, 담는 쪽이 C 에서 A 로 올라가도 이 인코딩은 그대로입니다.

**다른 저장소로 넘길 때는 `handoff/<받는 쪽>/` 에 둡니다.** 내는 쪽이 받는 쪽의 저장소에 직접 쓰면, 쓰기 경계와 한 방향 의존이 보장하는 아키텍처 경계의 증명이 그 자리에서 소멸합니다. 넘기는 쪽은 자기 저장소만 건드리고 경로만 알리며, 무엇을 반입할지는 받는 쪽이 결정합니다. 인계 번들은 스냅샷이므로 `HandoffFixtureTest` 가 지금의 인코더와 같은 칸을 쓰는지 대조합니다.

**파일로 쓰는 쪽은 시나리오 구동기입니다.** v1 에서 그것은 시험이며, 한 벌은 `picasso/build/export/run-1` · `run-2` · `run-3` 에 나옵니다. **앞의 둘은 같은 시나리오를 두 번 돌린 것입니다** — 두 벌의 해시가 같고 `runId` 만 다른 것이 그 값이 존재하는 이유이고, 읽는 쪽은 그 두 벌로 «둘째 구동이 새 사건으로 들어온다» 를 회귀로 박습니다. **`run-3` 은 재실행이 아니라 다른 시나리오입니다** — 같은 기체가 같은 분류로 거듭 깨지는 한 벌이며, 재발을 세는 쪽이 그 셈을 실물로 한 번 밟게 하는 자리입니다(§15.182). 따라서 **시험을 돌려야 한 벌이 갱신됩니다** — C 를 고른 대가이고, 승격하면 그 제약이 사라집니다.

| 항목 | 규약 |
|---|---|
| 파일 | `incidents.jsonl` · `remedy-searches.jsonl` **둘로 나눕니다.** 합치면 읽는 쪽이 하위 범주를 다시 나눠야 하고, 그 분류 규칙이 두 곳에 생깁니다 |
| 줄 | 한 줄에 한 기록. 배열이 아니라 줄인 이유는 **덧붙이기가 줄 추가로 그대로 옮겨지기** 때문입니다 |
| 순서 | 열린 순서. `incidentId` · `searchId` 는 **불투명한 값**이며 분해하지 않습니다 |
| 완료 신호 | 임시 파일에 쓰고 **이름만 바꿉니다**(동일 파일 시스템). 마지막에 `manifest.json` 이 나타나는 것이 한 세트가 모두 나왔다는 신호입니다 |
| 필드 이름 | 코틀린 속성 이름 그대로(lowerCamelCase). 계약 메시지와 열거는 **protobuf JSON 규약**을 따릅니다 — 기존 적재 API 표면이 이미 그 규약이므로 다르게 쓰면 갈립니다 |
| 없음 | **키를 빼지 않고 `null` 을 적습니다.** 빼면 값이 없다는 것과 이 버전이 아직 그 필드를 내지 않는다는 것이 같은 모양이 됩니다. 빈 목록도 `[]` 로 적습니다 |
| 시각 | `at` 은 가상 시계, `wallClockAt` 은 실제 시계. 둘 다 ISO-8601 |
| 레지스터의 하위 범주 | 한 줄에 **평평하게** 적습니다. `outcome` 이 `FOUND` · `NONE` · `WITHHELD` · `SOURCE_MISSING` 중 하나입니다. 앞의 셋은 케이퍼빌리티 연쇄의 탐색이 낸 응답이고 `SOURCE_MISSING` 은 셀 자리의 점유가 낸 응답이며, **한 레지스터에 두는 이유는 작업 수락 게이트가 첫 거부에서 되돌아가기 때문입니다** — 한 번의 작업 수락은 많아야 한 번 거절되고 그 거부에 대한 응답은 하나뿐입니다(§15.183). 채택(`adopt`)은 후보마다 그 기체의 작업 수락 거부와 같은 줄을 남기므로 채택 한 번이 후보 수만큼 줄을 낼 수 있지만, 열쇠 하나에 응답 하나라는 규칙은 그대로입니다(§15.229). `FOUND` 가 곧 활성 제안은 아닙니다 — 개정의 거부는 줄만 남기고 제안을 세우지 않습니다(ADR 46) |
| 출발 결품 | `SOURCE_MISSING` 이 `material` · `source` · `observed` · `alternatives` 를 싣습니다. **`alternatives` 는 널과 빈 목록이 다릅니다** — 널은 셀이 그 질문에 답하지 않은 것이고 빈 목록은 그 자재를 든 자리가 하나도 없다는 응답이며, 접으면 못 물어본 것이 재고 부족으로 읽힙니다. **`observed` 의 널은 빈 자리입니다** — 셀이 그 자리가 비었다고 답한 것이고, 값이 있으면 거기 있는 다른 식별 정보입니다. 같은 줄의 `alternatives` 와 널의 뜻이 반대라서, 한 규칙으로 읽으면 빈 자리가 못 본 것으로 읽힙니다. 셀이 답하지 않은 출발 자리는 판정하지 않으므로 이 줄이 아예 생기지 않습니다. 단, 출발 관측 선언이 `REQUIRED`인 단위는 판정하되 조치 탐색 레지스터 줄 없이 거부로만 나갑니다. **`steps` 키가 없습니다** — 가려서가 아니라 승인할 것이 없어서이며, 어느 자리를 쓸지는 작업 지시를 고치는 쪽의 결정입니다 |
| 보류 | **`outcome` 이 `WITHHELD` 인 줄에는 `steps` 키가 없습니다.** 적재면의 방벽이며 코드의 방벽과 같은 성질입니다 — 내보내는 쪽이 편의로 제안 표에서 조치 시퀀스를 꺼내 실으면 조회 한 번으로 보류가 해제됩니다. 구현 PR 이 이 줄을 결함 주입으로 확인합니다 |
| 인시던트가 드는 것 | 어느 기체(`robotId`) · 근거의 세기(`requiredEvidence`·`reachedEvidence`·`verification`) · 분류의 근거(`fault`) · 단계 위치(`step`)를 함께 적습니다. **읽는 쪽이 되짚지 않도록 하는 것이 기준입니다**(§15.177) |
| 결함 | `fault` 는 이 단위의 분류가 그 값이 된 근거이고, `blockedBy` 는 **다음 단위를 막는** 결함입니다. 다음 단위가 없으면 후자는 빈 목록이므로 둘은 다른 차원입니다. 정준 분류와 벤더 원문을 함께 실으며, 분류 이름만으로 접지 않습니다 |
| 의도 | `intent` 가 **상위가 적은 것과 이 계층이 편 것을 함께** 싣습니다. 앞은 작업 마스터·버전·작업 지시 값·자재·설비이고 뒤는 스킬·단위 값·출발·도착·기대 식별자이며, 둘이 갈리는 자리가 곧 이 계층의 번역입니다. 케이퍼빌리티의 최고 등급과 시간 윈도우 폭도 함께 실어 `evidenceWindow` 가 **왜 그 범위였는지**를 답합니다 |
| 경로 | `route` 가 `ROBOT` · `FLEET` · `SIGNAL` 중 하나입니다. `SIGNAL` 은 설비 대기이며 하위 요청 없이 이름 있는 신호를 기다린 단위이므로 책임 소재는 셀 설비와 현장 쪽입니다(버전 `6` 에서 생긴 하위 범주). **없으면 책임 소재를 가르지 못합니다** — 같은 실패라도 앞은 기체와 어댑터의 일이고 뒤는 플릿의 일이며, 다음에 누구에게 물을지가 그것으로 갈립니다 |
| 관측 신뢰 | `observation` 이 `linkBroken` · `lateEvents` · `progressObservable` · `progressStalled` 를 싣습니다. **`progressObservable` 은 3값이며 널이 「아직 갱신을 못 봤다」입니다** — 거짓으로 접으면 못 물어본 것이 못 재는 것이 되고, 진행률을 내지 않는 기종이 언제나 정지한 것으로 보입니다 |
| 단계 위치 | `step` 은 `at`(1부터) · `plan`(순서대로) · `completed` 입니다. **총수는 `plan` 의 길이이며 따로 싣지 않습니다** — 같은 사실을 두 칸에 두면 갈릴 자리가 생깁니다 |
| 버전 | `schemaVersion` 이 `6` 입니다. `2` 에서 `blockedBy` 가 분류 이름의 배열에서 결함 객체의 배열로 **모양이 바뀌었으므로** 그 버전은 읽는 쪽이 보아야 하며, `3` 은 칸이 는 것뿐입니다. `4` 는 인시던트 줄을 바꾸지 않고 **조치 탐색 기록의 `outcome` 에 하위 범주를 하나 더합니다** — 칸이 느는 것과 달리 `outcome` 으로 분기하는 읽는 쪽은 모르는 값을 만나므로 그 자리만 버전을 보면 됩니다 · `5` 는 인시던트 줄에 `resolution`(사람이 그 단위에 낸 판단) 한 칸을 더합니다 — 칸이 느는 것이라 읽는 쪽이 안 보아도 깨지지 않고, **요약은 안 바뀝니다**(해시에서 빠지는 셋째 칸입니다) · `6` 은 인시던트 줄의 `route` 에 하위 범주 `SIGNAL`(설비 대기)을 하나 더합니다. 칸은 늘지 않았으나 `route` 로 분기하는 읽는 쪽은 모르는 값을 만나므로 `4` 와 같은 이유로 버전을 보아야 합니다. 인시던트의 임무 버전(`Intent.missionVersion`)은 해시에 들지만 읽는 쪽이 없어 내보내지 않습니다(ADR 9). 그래서 **모든 줄의 요약(`digest`)이 바뀝니다**(코드 케이퍼빌리티의 줄도 포함). 읽는 쪽이 `digest` 를 멱등성 키로 쓰면 다시 산출한 세트를 새 인시던트로 받습니다. 인시던트의 현장 설정 버전(`Intent.siteSettingsVersion`)과 그 라운드의 `inDoubtGrace`·`stallWindow` 도 내보내지 않습니다(ADR 9). 해시에는 설정 버전이 있을 때만 한 줄이 들어가므로, 설정 없이 도는 줄의 요약은 바뀌지 않고 버전도 `6` 그대로입니다 |
| 번들의 해시 | `digest` 를 함께 적습니다. 이미 계산되는 값이며, 읽는 쪽이 같은 인시던트를 두 번 받았는지 가르는 유일한 결정적 조회 키입니다 |
| 한 세트의 명세 | `manifest.json` 이 `schemaVersion` · `runId` · `writtenAt` · `virtualNow` · `contractSemver` · `counts` 를 싣습니다 |
| 런 식별자 | `runId` 는 **이 내보내기에서 유일하게 결정적이지 않은 값**입니다. 나머지는 같은 시드면 같은 값이고 그것이 재현의 근거인데, 읽는 쪽이 멱등성 키를 그 값들로 들면 같은 시드의 두 번째 구동이 전부 이미 본 것으로 접혀 **아무 신호 없이** 처리가 사라집니다. 실제 시계에서 나오며 같은 순간에도 겹치지 않습니다. **결정적으로 바꾸면 그 고장이 조용히 돌아옵니다** |

## 7. 승인면의 모양 (ADR 44)

§6 이 정한 것은 **읽기**입니다. 승인은 쓰기이며, 파일 왕복으로는 시도한 자리에서 허락과 거부를 받을 수 없으므로 규약이 다릅니다.

**본 계층은 여전히 소켓을 인지하지 않습니다.** `ApprovalWire` 는 문자열만 생성하고 해석하며, 전송은 담는 측의 몫입니다. §6 의 인코딩과 동일한 성질입니다.

### 7.1 부르는 측이 할 수 있는 말은 하나입니다

승인 시도는 **조치를 기술하지 않습니다.** 이미 본 계층이 계산하여 거절한 제안 하나를 가리킬 뿐이며, 작업 지시도 단계도 값도 실을 칸이 존재하지 않습니다. 호출자의 권한이 "승인 시도 한 번" 을 넘지 않는 것은 규율이 아니라 API 표면의 형상에 기인합니다.

| 요청 필드 | 규약 |
|---|---|
| `approverId` | 누가 누르는가. **위조 가능하며 부인방지가 아닙니다**(§15.3). 판정은 본 계층에서 수행하므로 부르는 측이 위조할 수 없는 것은 판정입니다 |
| `approverKind` | `PERSON` 또는 `AGENT`. 감사에 남고 이의율을 가르는 차원입니다(ADR 43) |
| `robotId` · `jobOrderId` | 가리킬 제안의 조회 키. 작업 지시 본문이 아니라 식별자입니다 |
| `sawSkillTypes` | 부르는 측이 읽은 조치 시퀀스. 지금 제안과 다르면 거절합니다. **비워 두는 경로를 두지 않습니다** |
| 그 밖의 필드 | 읽지 않습니다. 자격 주장을 기재해도 판정에 도달하는 경로가 없습니다 |

**해독 불가능한 요청은 거부가 아니라 오류입니다.** 둘을 동일한 형태로 전달하면 읽는 측이 자기 오타와 자격 부재를 구별하지 못합니다.

### 7.2 값은 선언과 관측에서만 옵니다

| 파라미터 | 출처 |
|---|---|
| 계약이 `is_object_reference` 로 표기한 칸 | **관측** (`HoldState.objectRef`) |
| 그 밖의 필수 칸 | **선언** (`Entitlement` 의 `DeclaredAction.parameters`) |

- 생성하는 경로는 존재하지 않습니다. 어느 쪽도 충족하지 못하면 거부며 사람에게 위임됩니다
- 선언이 대상을 기재한 경우 관측과 일치해야 하며, 관측을 덮어쓰지 못합니다
- 관측은 **승인 시점에 다시 확인합니다.** 제안 수립 시점의 값을 보관하면 낡은 사실로 승인이 성립합니다
- 단계마다 효과로 파지를 전진시키므로, 둘째 단계가 파지할 대상의 명칭은 존재하지 않으며 거절합니다(§15.174)

### 7.3 거부는 값이며 오류가 아닙니다

거부 종류를 열거형으로 제공합니다. 사유 텍스트만 제공하면 읽는 측이 문자열 대조에 의존하게 되며, 그 검증은 거부의 발생만 확인하므로 자격 부재와 제안 부재를 구별하지 못합니다. 종류를 구분하는 기준은 **후속 조치의 상이 여부**입니다.

| 종류 | 후속 조치 |
|---|---|
| `WITHHELD` | 사람이 먼저 진단합니다. 자격으로 관통되지 않으며, **보류가 자격보다 먼저 판정됩니다** |
| `NO_PROPOSAL` | **이 프로세스가 뜬 뒤로 그 (기체, 작업 지시)에 제안이 선 적이 없습니다.** 탐색 레지스터에서 그 조회 키의 응답을 읽습니다. 그 사이 새 제안이 서지 않는 한 다시 시도해도 같습니다. 이 프로세스의 탐색 레지스터에 그 조회 키의 `FOUND` 가 있다면 이미 승인을 든 실행의 개정 거부에서 난 것입니다 — 그 작업 지시는 이미 실행으로 서 있고, 판단 기록이 승인 하나만 실으므로 그 개정은 제안을 세우지 않습니다(ADR 46, §15.289) |
| `CONSUMED` | **이미 소모됐습니다**(ADR 46). 응답의 `consumed` 칸이 누가·언제·어느 실행으로·무엇을 보냈는지 싣습니다. 그 승인자가 자기 id 면 실행의 근거를 기다리고, 아니면 누가 무엇을 보냈는지 확인합니다 |
| `PROPOSAL_CHANGED` | 다시 읽고 다시 시도합니다 |
| `NOT_DECLARED` | **원래 없었습니다.** 선언을 등록합니다 |
| `REVOKED` | **전에 허락되었다가 회수되었습니다.** 철회 사유를 확인하고 **사후 검토로** 갑니다. 선언을 다시 올리는 자리가 아닙니다(ADR 45) |
| `EXPIRED` | 기간이 지났습니다. 갱신합니다. **철회가 이보다 먼저 판정됩니다** — 둘 다인 경우 만료를 먼저 내면 기간만 연장되어 철회가 조용히 되돌아갑니다 |
| `ROBOT_OUT_OF_SCOPE` · `SKILL_OUT_OF_SCOPE` | 범위를 확대하거나 사람이 승인합니다 |
| `VALUE_NOT_DECLARED` | 선언에 값을 기재합니다 |
| `OBJECT_NOT_OBSERVED` · `DECLARED_CONTRADICTS_OBSERVED` | 사람이 확인합니다. 관측이 없거나 선언과 어긋나면 자동으로 누르지 않습니다 |
| `CAPABILITY_UNKNOWN` | 기체와의 연결을 복구합니다 |
| `VALUES_NOT_ACCEPTED` | 값을 빼고 다시 시도합니다 |
| `REFUSED_BY_GATE` | 자격의 문제가 아닙니다. 조건이 해소되면 같은 제안이 그대로 섭니다 |
| `REMEDY_NOT_APPLIED` | 조치 시퀀스가 나가지 않았습니다. 그 작업 지시가 이미 실행으로 서 있을 때 네 조건(승인의 버전이 실행의 버전보다 높다, 실행이 제안의 기체에 서 있다, 실행이 아직 승인을 들지 않았다, 실행이 끝나지(`ABORTED`, `PHYSICALLY_DONE`) 않았다) 중 하나라도 어긋나면 승인은 조치 시퀀스를 싣지 못합니다. 승인으로 집계되지 않고 소모로도 남지 않습니다(§15.175, 닫힘 §15.289, ADR 46) |

**게이트 거부는 제안을 소모하지 않습니다.** 소모할 경우 조건 해소 후 사람이 승인할 대상까지 소멸합니다.

**소모는 기록으로 남습니다**(ADR 46). 승인이 작업 수락으로 이어져 제안이 지워질 때 (기체, 작업 지시)마다 소모 기록 하나가 남고, 활성 제안이 없는 자리에 다시 온 승인은 그 기록을 `CONSUMED` 로 받습니다. 거부 응답의 `consumed` 칸은 `CONSUMED` 에서만 차고 다른 거부는 `null` 이며, 승인 응답은 그 칸을 싣지 않습니다. 이 값과 칸이 들어온 것이 승인 호스트 규약의 버전 3 입니다. 기록도 프로세스 수명과 같으므로(§15.166) 다시 뜨면 소모됐던 조회 키도 `NO_PROPOSAL` 을 받습니다. 개정의 연쇄 거부는 이제 제안을 세우지만, 이미 승인을 든 실행의 개정은 제안을 세우지 않으므로 소모를 가리지 않습니다 — 그 실행의 열쇠에는 소모 기록이 서 있고 판단 기록(`JudgmentRecord`)의 `approval` 칸도 승인 하나만 싣기 때문입니다(§15.175, 닫힘 §15.289).

**철회는 사람의 승인을 막지 않습니다.** 사람은 선언 없이 승인하므로 철회가 라인을 정지시키지 않습니다. 정지시킬 경우 아무도 철회를 사용하지 않게 되며 그 시점에 본 장치가 무력화됩니다 — 만료를 짧게 설정할 수 있는 근거와 동일합니다.

**철회의 기록은 선언에 표시로 남으며 본 계층은 그것을 읽기만 합니다**(ADR 45). 삭제로 구현할 경우 선언 조회가 널을 반환하고, 그것은 `NOT_DECLARED` 와 동일한 형태가 되어 후속 조치가 정반대인 두 상태가 접힙니다. 권한 강등의 주체는 선언의 소유자이며, 자동 승인한 조치의 실패 사실은 인시던트 번들의 `approvedBy` 로 이미 외부에 전달됩니다(§15.168).

**승인의 응답이 실제 전달된 값을 반환합니다.** 호출자가 값을 선택하지 않았으므로, 자기 명의로 전달된 내용을 확인하는 경로가 이것뿐입니다.

**모든 응답이 인스턴스를, 단계마다 단위를 싣습니다**(ADR 48, 버전 4). `instanceId` 는 응답을 낸 인스턴스이고 `executionId` 는 그 인스턴스 안의 셈이므로, 둘을 짝지어야 다시 뜬 뒤에도 한 시도를 가리킵니다. 단계의 `unitId` 는 작업 응답(§8)가 그 단계를 부르는 이름입니다.

**사람의 문 거부도 같은 거부 종류와 소모 기록을 싣습니다**(§15.229). 프로세스 안의 함수인 `approveRemedy`의 거부(`Middleware.Submission.Rejected`)가 이제 밖의 문(`attemptApproval`)과 같은 판정에서 온 거부 종류(`approvalRefusal`)와 소모 기록(`consumedApproval`)을 싣습니다. 사람의 문은 승인 호스트를 지나지 않으므로 승인 호스트 규약은 버전 4 그대로입니다.

### 7.4 v1 에서 담는 측

§6 의 사다리와 동일한 판단을 적용하되 결론이 다릅니다. **읽기는 파일로 충분했으나 쓰기는 그렇지 않습니다.** 시도한 자리에서 허락과 거부를 받아야 하므로 왕복이 동기여야 하며, 이것이 §6 이 기재하지 않은 네 번째 승격 조건입니다.

| 조건 | 상태 |
|---|---|
| 조회가 실시간이어야 함 | 미충족 |
| 적재가 프로세스 수명을 넘어 남아야 함 | 미충족 (§15.166) |
| 읽는 측이 둘 이상 | 미충족 |
| **밖에서 들어오는 쓰기가 발생** | **충족** |

`registry` 가 담는 선택지(A)는 승인에 대해서는 부적합합니다. 설정 평면이 실행 평면의 적재를 드는 것이 읽기의 대가였다면, 쓰기에서는 설정 평면이 기체 연결까지 보유해야 합니다. **본 계층을 세우는 측이 승인면을 함께 냅니다.** v1 에서 실행 계층을 실제로 구동하는 주체는 시나리오 실행기며, 그것이 담는 측입니다.

**인코딩과 전송을 가르므로 담는 측이 바뀌어도 본 규약은 유지됩니다.** `ApprovalWire` 는 순수 함수이며, 인프라 없이 시험이 물립니다.

### 7.5 v1 에서 실제로 여는 자리

```bash
./gradlew :picasso:runApprovalHost
./gradlew :picasso:runApprovalHost --args="--port 8770 --seconds 1800"
```

실행기가 실행 계층을 세우고 **루프백에만** `POST /approvals` 를 엽니다. 본 API 표면은 식별 정보를 인증하지 않으므로(§15.3) 외부로 공개하지 않습니다. 두 레지스터는 §6 의 규약대로 파일로 계속 나가며, 읽기 경로는 변경되지 않습니다. 작업 응답도 같은 자리에 §8 의 형식으로 나갑니다.

실행기는 제안을 **넷** 세웁니다. 거부 종류마다 후속 조치가 상이하다는 것은 값으로 확인해야 하며, 하나만 세우면 그 차이가 관측되지 않습니다. 자리마다 랙 하나가 든 채 실패해 운영자 보류에 서고(인시던트가 하나씩 열립니다) 사람이 그 실행을 취소로 닫은 뒤 점검 순회를 내며, 거부의 근거는 기체 스냅숏의 손입니다. 든 채 **도는** 다른 실행이 기체를 쥐고 있으면 그 손에 든 것이 그 실행의 일이라 거부는 해도 제안을 세우지 않습니다(§15.319).

| 기체 | 시도하면 |
|---|---|
| `hum-02` | 승인됩니다. 목적지는 선언에서, 대상은 관측에서 취득합니다. 같은 자리를 다시 부르면 `CONSUMED` 와 소모 기록이 돌아옵니다 |
| `hum-04` | `WITHHELD`. 자격이 있어도 통과하지 않습니다 |
| `hum-05` | `ROBOT_OUT_OF_SCOPE` |
| `hum-03` | `NO_PROPOSAL`. 탐색이 `NONE` 을 산출했습니다 |

ADR 43이 「배치의 결정」이라 명시한 자리의 첫 구현체는 선언 파일을 읽는 `FileEntitlements`입니다. 제공되는 `handoff/narrator/entitlements.json`은 picasso 시험과 `ScenarioHost` 시연을 위한 픽스처이며 배치 선언의 복사 원본이 아닙니다. 실제 배치는 해당 환경의 기체, 짧은 만료 시각, 자체 승인자 id를 담아 선언 파일을 따로 작성해 사용합니다. **해독 불가 시 빈 목록으로 접지 않고 기동에 실패합니다.** 접을 경우 오타가 있는 선언 파일이 "아무것도 선언하지 않음" 과 동일한 형태가 되며, 그 배치는 자동 승인 전건 거부를 정상으로 인식합니다.

**첫 승인이 성립할 때까지 가상 시계를 정지합니다.** 성공하는 승인은 파지 중인 대상의 명칭을 관측에서 취득하므로, 호출 이전에 기체가 적재물을 놓으면 그 출처가 소멸합니다. 거부 세 하위 범주는 값 충족 이전에 판정되므로 시계와 무관합니다.

**참조 실행기는 시험 소스에 남습니다**(§15.176). 담는 쪽의 부품 셋은 프로덕션 모듈 `host-kit` 으로 나왔지만(§15.314), 실행기 자체는 배포 가능한 프로세스가 아닙니다.

**승인 호스트는 루프백(`127.0.0.1`)에만 열리고 식별 정보를 인증하지 않습니다(§15.3).** 경로는 `POST /approvals` 입니다(근거 코드 `ApprovalHost`, 근거 시험 `ApprovalHostTest`). 응답의 `Content-Type` 은 늘 `application/json; charset=utf-8` 입니다. 실행기는 요청의 `Content-Type` 을 보지 않고 본문을 `UTF-8` 로 읽습니다. 이 두 가지는 시험이 대지 않으므로 보증이 아니라 지금 구현의 사실입니다.

| 상태 코드 | 규약 | 근거 시험 |
|---|---|---|
| `200` | 승인(`APPROVED`)과 거부(`REFUSED`) 모두에 돌아옵니다. 본문은 승인 호스트 버전 4 응답(`ApprovalWire`)입니다. | `밖에서 온 호출이 승인으로 서고 실린 값이 돌아온다`, `같은 제안에 두 번 승인하면 둘째는 소모로 거절된다` |
| `400` | 못 읽는 요청에 돌아옵니다. JSON이 아니거나, 필수 칸 다섯(`approverId`, `approverKind`, `robotId`, `jobOrderId`, `sawSkillTypes`) 중 하나가 없거나, 칸의 타입이 틀리거나, `approverKind` 가 `PERSON`·`AGENT` 밖의 값일 때입니다. 본문은 `{"error": "<사유>"}` 입니다. | `못 읽는 요청만 오류이고 거절은 정상 응답이다` |
| `405` | `POST` 가 아닌 메서드에 돌아옵니다. 본문 모양은 `400` 과 같습니다. | `POST 가 아니면 받지 않는다` |

**실행기 인자는 두 개씩 짝지어 읽으며, 모르는 플래그와 짝 없는 인자는 조용히 버립니다.** 오타가 나면 기본값으로 돕니다. 상대 경로는 `picasso/` 모듈 디렉터리 기준으로 풀리므로(Gradle 실행 태스크의 작업 디렉터리), 절대 경로를 권합니다. 포트는 기체 넷에 제안을 세운 뒤에야 열리며 그 전에는 연결이 거부됩니다. `hum-02` 의 승인은 프로세스마다 한 번뿐이며(다음부터 `CONSUMED`), 처음부터 다시 하려면 실행기를 다시 띄워야 합니다. 그때 `instanceId` 가 새로 나고 내보내기 파일들을 새로 씁니다(근거 코드 `ScenarioHost.main`).

| 인자 | 기본값 | 설명 |
|---|---|---|
| `--port` | `0` | 빈 포트 아무거나 씁니다. 실제 주소는 기동 안내 첫 줄에 찍힙니다. |
| `--seconds` | `600` | 그 시간이 지나면 승인 호스트가 닫힙니다. |
| `--export` | `build/export/live` | 두 레지스터와 `job-responses.jsonl` 이 나가는 자리입니다. |
| `--entitlements` | `../handoff/narrator/entitlements.json` | 자동 승인 자격 선언 목록입니다. 기본 파일은 시험과 시연을 위한 픽스처이며 배치 선언의 복사 원본이 아닙니다. 등록된 승인자는 `narrator-1`·`narrator-3`·`narrator-4` 뿐이라 다른 승인자 id로 부르면 `NOT_DECLARED`가 발생합니다. 다른 승인자로 시험하려면 같은 모양의 선언 파일을 직접 작성하여 전달합니다. |

**해시에 드는 것과 아닌 것.** 봉인 시점에 확정되고 같은 시드면 같은 값인 것은 전부 듭니다. 새로 들어온 기체·근거 등급·대조 결과·단계 위치·결함 원문·의도·경로·관측 신뢰가 모두 그러하며, 그중 하나가 다른 인시던트는 다른 인시던트입니다. 실제 시계(`wallClockAt`)와 나중의 판정(`review`)만 빠집니다. **맵은 키 순서로 정렬해 적습니다** — 순회 순서가 해시를 바꾸면 같은 인시던트가 두 값을 갖습니다.


## 8. 작업 응답의 바깥 형식 (ADR 48)

작업 응답(`JobResponse`)는 상위에 내는 것이고, 밖의 소비자는 그것을 실행의 완료 근거로 씁니다. **본 계층은 문자열만 만듭니다**(`ResultExport`). 꺼내고(`pending()`) 나르고 닫는(`ack`) 것은 본 계층을 세우는 담는 측이며, §6 · §7 과 같은 가름입니다.

| 항목 | 규약 |
|---|---|
| 파일 | `job-responses.jsonl` 이라는 이름을 줍니다. 어디에 어떤 주기로 쓸지, 안내 파일을 둘지는 담는 측이 정합니다 |
| 줄 | 한 줄에 작업 응답 하나, 낸 순서대로입니다. **같은 통보가 다시 실릴 수 있습니다** — 나르는 쪽은 확인 전까지 다시 나르므로 최소 한 번 전달입니다. `jobResponseId` 로 거릅니다 |
| 버전 | 줄마다 `schemaVersion` 을 싣고 지금 `1` 입니다. 레지스터 한 세트와 달리 안내 파일이 버전을 들지 않습니다 — 안내 파일이 있을지는 담는 측의 결정입니다 |
| 인스턴스 | 줄마다 `instanceId` 를 싣습니다. `executionId` · `jobResponseId` 는 인스턴스 안의 셈이라 다시 뜨면 되풀이됩니다. **둘을 짝지어야 한 시도를 가리킵니다** |
| 실행 | `executionId` 가 그 통보의 실행이며 승인 응답의 `executionId` 와 같은 값입니다. 작업 지시에서 실행으로 가는 대응표를 따로 들 필요가 없습니다 |
| 칸 | 작업 응답의 칸 이름 그대로입니다. 상위 확인 상태(`ack`)는 싣지 않습니다 — 나르는 쪽의 상태이고, 실으면 같은 통보가 확인 전후로 두 모양이 됩니다 |
| 없음 | §6 과 같습니다. 빈 목록은 `[]`, 빈 표는 `{}` 이고 키를 빼지 않습니다 |
| `version` | 작업 지시의 버전입니다(ISA-95 대응). 시도를 가르지 못합니다 — 시도는 (`instanceId`, `executionId`) 가 가릅니다 |

**승인 응답과 잇는 칸**(버전 4). 승인된 조치 시퀀스는 실행 계획의 맨 앞에 단계 순서대로 서며 단위 이름은 `remedy-{n}-{skillType}`(n 은 1부터)입니다. 응답의 단계와 소모 기록의 단계가 이 이름을 `unitId` 로 싣고, 작업 응답의 `completedUnits` · `unverifiedUnits` · `inDoubtUnits` · `incompleteUnits` 가 같은 이름으로 그 단계를 가리킵니다.

**운영자가 결함을 수용할 때 작업 응답을 냅니다**(§15.229). `release`가 참을 돌려줄 때 `RUNNING`과 빈 `blockedBy`를 든 작업 응답 하나를 내며, 거짓을 돌려줄 때는 내지 않으므로 다시 불러도 더 나가지 않습니다. 전에는 내지 않아 마지막 작업 응답이 실행이 다음에 알릴 때까지 `OPERATOR_HOLD`와 수용한 결함의 `blockedBy`를 들었습니다. 작업 응답 형식은 버전 1 그대로입니다.

**차단·보류·미확정이 풀릴 때 작업 응답을 내고 하위의 요청 없는 취소는 운영자 보류로 세웁니다**(§15.230). 결함 게이트가 저절로 풀리거나 운영자 판단(`resolve`) 및 미확정 해소(조회 또는 개정 갱신 응답)로 상태가 달라지면 라운드 끝에 작업 응답을 내며, 직전 응답과 내용이 같으면 다시 보내지 않아 `release` 등과 중복되지 않습니다. 하위가 요청 없이 스스로 취소한 태스크는 다음 단위를 시작하지 않고 해당 단위를 운영자 보류(`OPERATOR_HOLD`)로 전환하며 인시던트를 엽니다. 스냅숏을 일시적으로 관측하지 못해도 이미 존재하던 결함 차단은 유지되어 안전하지 않은 단위 착수를 방지합니다. 작업 응답 형식은 버전 1 그대로입니다.

**리빌드한 실행에 첫 pump 전 취소가 걸려도 스냅숏의 기체 태스크에 붙어 취소를 전달하고 종결합니다**(§15.231). 담는 쪽은 `resume`으로 리빌드를 마친 직후 첫 pump가 실행되기 전이라도 곧바로 `cancel`을 호출할 수 있습니다. 첫 pump는 `StartTask`를 재전송하지 않고 스냅숏의 태스크 식별자로 핸들을 직접 구성해 로봇 단위에 부착한 뒤 하위에 취소를 보내며, 하위 태스크가 종료되면 종결합니다. 스냅숏을 읽지 못하면 즉시 중단으로 종결하지 않고 대기하며, 작업 허가가 차단되어 있어도 취소 전달은 막히지 않습니다. 단, 이 처리는 로봇 단위에만 적용되며 플릿 운반 단위는 대상에 포함되지 않습니다.

**v1 에서 실제로 쓰는 자리.** §7.5 의 실행기가 두 레지스터와 같은 자리에 `job-responses.jsonl` 을 씁니다. 담는 측의 참조일 뿐 실제 하드웨어 담는 측이 아닙니다 — 상위 확인을 하지 않으므로 같은 통보가 매번 다시 실립니다. 레지스터 한 세트의 안내(`manifest.json`)는 이 파일을 세지 않습니다. **실제 하드웨어 담는 측은 아직 없습니다**(§15.203).

**실제 하드웨어 담는 측은 `picasso` 에도 koshei 에도 두지 않습니다.** 2026-10-04 바깥 루프(koshei) 쪽 결정에 따라, 실제 하드웨어 현장이 생기면 현장 운영 측이 소유하는 별도 배치 저장소에 두고 그 저장소가 `picasso` 를 라이브러리로 씁니다. 이는 ADR 48의 "쓰기는 담는 측"과 같은 방향입니다. 라이브러리로 가져갈 수 있는 것은 `picasso` 의 `ApprovalWire`, `ResultExport`, `Middleware.instanceId` 와 프로덕션 모듈 `host-kit` 의 `ApprovalHost`, `FileEntitlements`, `BundleWriter` 입니다. 참조 실행기인 `ScenarioHost` 만 시험 소스에 남았으므로 배포 저장소는 이 부품들을 엮어 호스트를 구성합니다. 그때까지 koshei 는 §7.5의 실행기를 연결 시험 상대로 씁니다.

**담는 측이 지킬 조건으로, `job-responses.jsonl` 은 그 인스턴스의 처음부터의 전체 이력이어야 하고 확인된 통보를 앞에서 잘라 내면 안 됩니다.** koshei 는 첫 줄의 `instanceId` 로 어느 구동인지를 읽기 때문입니다. 참조 실행기는 이 조건을 지킵니다(확인된 것까지 포함한 작업 응답 전체를, 개수가 늘 때만 원자적으로 다시 씁니다).

**설계 변경 이력 §15.224 에서 `Middleware.forget(executionId)` 를 추가하여 담는 측이 끝난 실행을 명시적으로 이빅션하면 그 실행을 실행 표에서 빼고 그 실행의 작업 응답(전부 상위가 확인한 것)을 아웃박스에서 빼며, 확인되지 않은 작업 응답이 남은 실행은 이빅션이 거부됩니다.** 그래서 이빅션을 쓰면 아웃박스(`responses()`)는 그 인스턴스의 처음부터의 전체 이력이 아니므로, 이빅션을 쓰는 담는 측은 `job-responses.jsonl` 을 `responses()` 로 통째로 다시 쓰지 말고 내보낸 작업 응답을 이빅션하기 전에 이어 붙여야 위의 전체 이력 조건을 지킵니다. 참조 실행기는 `ack` 을 하지 않으므로 이빅션이 거부되어 지금처럼 통째로 다시 써도 조건이 지켜집니다. 첫 소비자인 mission-ops는 `forget`을 호출하며, `responses()`로부터 통째로 다시 쓰지 않고 각 작업 응답을 추가 전용 송신 기록의 한 행으로 추가 적재합니다(설계 문서 §15.225).

## 9. 판단 기록의 바깥 형식

판단 기록(`JudgmentRecord`)은 실행 하나에서 이미 정해진 것(이 계층의 판정, 사람의 판단·수용한 결함·승인 소모, 그 시각)입니다. 담는 측이 `Middleware.judgmentRecord(executionId)` 로 꺼내 영속하고, 재기동 때 `Middleware.resume(…, record)` 에 넘깁니다. 리빌드는 옮기기만 하고 다시 판정하지 않습니다. **본 계층은 문자열만 만듭니다**(`JudgmentRecordWire.encode`·`decode`). §6 의 `LedgerExport`, §7 의 `ApprovalWire` 와 같은 가름이며 파일·저장소·시계를 건드리지 않습니다. 어디에 언제 쓸지는 담는 측이 정합니다.

| 항목 | 규약 |
|---|---|
| 버전 | 최상위 `schemaVersion` 이 문자열 `"3"` 입니다. 칸이 늘거나 값이 늘면 버전을 올립니다. 모르는 칸을 무시하는 읽기를 두지 않기 때문입니다. 버전 2 에서 최상위 칸 `cancelRequested`가, 버전 3 에서 단위 칸 `everHeld`·`heldInEarlierAttempt`가 늘었습니다. 버전 1·2 기록도 읽습니다. 버전 1 기록은 `cancelRequested` 칸 없이 읽고 취소가 걸리지 않은 기록이 되며, 버전 1·2 기록은 두 단위 칸 없이 읽고 쥔 것을 본 적 없는 단위가 됩니다 |
| 최상위 칸 | `schemaVersion`, `jobOrderId`, `orderVersion`(정수, 기록이 선 작업 지시 버전), `acknowledgedFaults`(문자열 배열, 수용한 결함의 열쇠), `approval`, `units`, `cancelRequested`(참거짓, 실행에 취소가 걸렸는가. 버전 2 부터) 입니다 |
| `approval` | 널이거나 `robotId`(제안의 열쇠가 된 기체), `approverId`, `approverKind`, `at`(가상 시계), `wallClockAt`(실제 시계), `steps` 배열(`unitId`, `skillType`, `parameters` 문자열 표)입니다. 리빌드할 때 이 걸음이 계획 앞에 이 순서로 다시 섭니다. 실행 id 는 싣지 않습니다(인스턴스 안의 셈, ADR 48) |
